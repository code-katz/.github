# `/ck:do`: one sentence in, the team's work out

**Status:** proposal for Will's approval, 2026-10-06. Nothing is built. Supersedes the phase-two `/ck:feature` row in the phase-one PRD (§10.1): same work, with a front door that picks the team.

## 1. Why

On 2026-10-05 Will typed, in a game project, "start a task with the right team member(s) to update the rule book so that the icons we use are associated with the rulebook entries. I want to see a mockup to approve." The session improvised: it chose Kai and Sasha itself, wrote a lane prompt by hand, and offered it as a task card to run in a worktree. That is the old team tool's pattern. It ran Kai as a whole session on the session's model, not on Kai's tier; recorded no cost; produced whatever mockup that session decided to make instead of a gallery of labeled variants on a page; tied nothing to the PRD, the brand guide, or the design folder; and would have started Sasha from a hand-written brief with no acceptance checks before Will saw a diff.

`/ck:do` is the version of that sentence where the same request produces a plan Will approves, the ck pieces run in the background on the right tiers with a review page at each gate, the build happens in a worktree with checks and a second-model verification, and everything is recorded.

## 2. Users and journey

Will and Clare, on any project where ck is installed and at least a PRD exists. Journey J4:

1. Clare types `/ck:do Put each entry's icon beside its heading in the Rulebook; I want a mockup to approve first.`
2. River answers in one numbered message: what kind of work this is, the steps, who owns each, what Clare will be asked to approve and when, the files the build will touch, and the rough cost. Nothing else has run.
3. Clare says yes, or changes a step, or says no.
4. The steps run in the background. At the first gate she gets a gallery page with labeled variants; she comments, says "done", approves the proposed changes, and picks one.
5. The build runs in a worktree; Robin's acceptance checks run; a second model verifies against the chosen variant and the checks. Clare gets a review page with the diff summary, the screenshots, and the check results, and says ship or change.
6. On ship, the branch is merged (or a pull request is opened, per the project's convention), the run record is final, and `/ck:next` knows about it.

## 3. The command

`/ck:do <task in a sentence or two>`. A skill (`skills/do/SKILL.md`) owns the gates; three workflows do the stage work. No agent runs before the author approves the plan.

### 3.1 Triage (inline, one agent: River on Fable 5.1)

Reads the request and whatever exists of `docs/PRD.md`, `docs/TEAM.md`, `docs/brand-guide.md`, `docs/design/`, `ROADMAP.md`, `docs/ARCHITECTURE.md`, and the repository's top-level layout. Writes `<runDir>/plan.json` and returns the plan: `kind` (design, build, document, decision, mixed), `steps` (each with owner persona, the ck piece it uses, the gate it ends in, the files it may touch), `requirement` (the PRD requirement or roadmap item it serves, or "none, new"), `estimate` (agents and dollars from the measured drills), and `questions` (what River would have asked, with the assumption it proceeds on). The skill prints the plan as a numbered message and stops.

Rules for triage: use the team document's owners when it exists; a design step always goes through `/ck:design`'s gallery; a decision always goes through `/ck:panel`; a document step goes through the document's own command; a build step never starts without a gate before it that produced the thing to build (a chosen variant, an approved document, or the author's explicit "no mockup, just build it").

### 3.2 Approve (the skill, AskUserQuestion or chat)

"Yes", "no", or a change. A change re-runs triage with the change as an extra constraint, once. Record the approved plan in `run.json`.

### 3.3 Run the gates (existing pieces)

- Design step: `Workflow("ck:design-round", { stage: "variants", ... })` as `/ck:design` does, then the gallery review per `skills/review-page`, then `stage: "refine"` for the chosen variant and the spec with Robin's acceptance checks.
- Decision step: `Workflow("ck:panel", ...)`; the memo is the gate's page.
- Document step: the document command's workflow, then its review.

### 3.4 Build (new workflow: `workflows/build.js`, phase two's parallel-build research)

Inputs: the chosen variant and spec, or the approved document, the files the plan allows, the owner persona, the project's test command if any.

1. **Slice.** The owner (Sasha for UI, Akira for backend, the plan's owner otherwise) reads the spec and writes `<runDir>/slices.json`: one to three independent slices with no file overlap, each with its acceptance checks from the spec and its files. One slice is the common case.
2. **Build, in parallel, one worktree per slice.** Each slice's agent works in `git worktree add <runDir>/wt/<slice> -b ck/<runId>/<slice>` on the owner's tier, touches only its files, runs the project's lint and tests when they exist, and commits. Scripts cannot create worktrees; the skill creates them before launching and removes them after merge.
3. **Verify, on a different model.** For each slice a neutral verifier on a model other than the builder's (Sonnet 5 for an Opus or Fable builder, Opus 5 for a Sonnet builder) checks the diff against the acceptance checks and the chosen variant: every check `met`, `unmet`, or `cannot tell`, with the evidence. For UI slices it renders the screens with the existing gallery renderer from the built code's own HTML where the project is web-based; otherwise it reads the diff.
4. **Fix once.** Unmet checks go back to the builder for one revision with the smallest-edits rule; the verifier runs again.
5. **Report.** `<runDir>/build.md`: per slice, the diff summary, the check table, the screenshots, the cost; published as the build's review page with the question "Ship it, or what should change?"

The skill merges each slice branch into the working branch on "ship" (or opens a pull request when the project has `.github/` and a remote), deletes the worktrees, and sets the run final. A merge conflict between slices is the skill's to report, never to resolve silently: "Slices A and B both changed `<file>`; I will merge A and re-run B on top of it" is one question to the author.

### 3.5 Run record

`.ck/runs/<timestamp>-<slug>-do/` with `run.json` (plan, approvals, harness run ids per stage, status), `plan.json`, the design or panel files, `slices.json`, `build.md`, and a `review.md` per gate. Documents and galleries land where their own commands put them (`docs/design/<slug>/`, `docs/decisions/`).

## 4. What it costs

From the measured drills: triage about $1.50 (one Fable pass over the project documents); a design round about $10 (drill 10); a panel about $5; a one-slice build about $6 to $12 (builder on its tier plus a cheaper verifier, one fix) and about $4 more per extra slice. The rulebook example: triage, one design round, one build, about $20. The plan states the estimate before the author approves.

## 5. Acceptance

1. On the ck-test project, `/ck:do` with a one-sentence design-and-build task produces a plan with the right owners from `docs/TEAM.md`, waits for approval, runs a gallery review, builds the chosen variant in a worktree, verifies on a second model, and shows a build page; "ship" merges the branch and the run is final. Nothing ran before the approval.
2. On a project with no `docs/TEAM.md`, triage still picks owners from the roster and says it did.
3. A build step with no gate before it and no explicit "just build it" is refused in the plan with the reason.
4. A verifier never runs on the builder's model.
5. Every stage has a harness run id in `run.json`; the drill cost can be computed by the shared method.
6. The build never touches a file outside the plan's list; a slice that tries is stopped by the verifier's check and reported.

## 6. Risks

- **Worktrees on the author's checkout.** Uncommitted changes in the working tree are the author's; the skill refuses to start a build while `git status` is dirty, and says so.
- **Verification on a different model is partial decorrelation**, as the panel's is. Robin's checks are the real oracle; the verifier reports evidence, it does not approve.
- **Scope creep in triage.** A plan with more than three steps or two gates is too big for one `/ck:do`; triage says so and proposes the first `/ck:do` of a sequence.
- **The build is where the parallel-build research binds for the first time.** The first drills will find what the design does not foresee; budget two drills before Clare uses it.

## 7. Order of work

1. `skills/do/SKILL.md` with triage, approval, and the design and panel gates (reusing the existing workflows). Drill on ck-test with a design-only task.
2. `workflows/build.js` with one slice, the verifier, and the build page. Drill with the rulebook task on the game project.
3. Multiple slices and the pull-request path. Drill.
4. Record the three drills, the cost, and what broke; then Clare's J4.

About a week of building, plus the drills' cost (three runs, about $60).
